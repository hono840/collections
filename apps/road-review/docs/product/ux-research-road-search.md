# UX リサーチ: 道の検索（入力しながら候補が出る）とお気に入り

- 作成: ux-researcher（CPO 配下）／作成日: 2026-10-10
- きっかけ: CEO の新しい方針（2026-10-10）
  - 主な機能を「**名前のついた道（峠・スカイラインなど）を検索する**」に変える。打っている途中で候補が出る（例: 「ヤビツ」→ ヤビツ峠、「スカイライン」→ 西伊豆スカイライン／箱根スカイライン …）。
  - 「道の登録」は「**検索結果をお気に入りにする**」ことに変わる。
  - 結果の画面では、地図（簡単な SVG でもよい）の上で、**道をなぞるように線が伸びる動き**を見せる。
  - スマホ最優先・シンプル・カラフル（`road-review-design-spec-v2.md` の方向を引き継ぐ）。
  - あとで、お気に入りの道に「走った記録・評価」を残す（`road-review-prd-v2.md` の走った記録はそのまま使う）。
- 表記: 【事実】出典で確かめた／【推論】根拠から考えた／【未確認】確かめられていない（確かめ方を書く）
- 文書の位置づけ: **調査と提案**。PRD・DS を書き換えるものではない。決まったら feature-planner（PRD）と ui-ux-designer（DS）が取り込む。

用語メモ:
- **候補（サジェスト）**: 打っている途中に、下に出る「これのことですか？」の一覧
- **コンボボックス（combobox）**: 「入力欄」と「候補の一覧」がセットになった部品の正式な名前
- **IME（アイエムイー）**: ひらがなを打って漢字やカタカナに変える仕組み（日本語入力）
- **変換中（コンポジション）**: IME で、まだ確定していない文字（下線が付いている状態）を打っている間
- **読み上げ（スクリーンリーダー）**: 画面の文字を声で読む機能（iPhone の VoiceOver など）
- **動きを減らす設定（reduced motion）**: 端末の設定で「動きを少なく」を選んだ人向けの表示

## 0. まとめ（先に結論）

1. **ホームの一番上に、いつも開いた検索欄を置く。** 虫めがねの記号だけにしない。NN/g の調査では、検索を「リンク」から「開いた入力欄」に変えただけで検索の利用が 91% 増えた（出典 N1）。
2. **候補は 1文字から、最大 6件、端末の中で探す。** 道のリストをアプリに入れておき、打った文字をサーバーに送らない（「データは端末の中だけ」という v2 の約束を守れる）。
3. **かなと漢字を同じに扱う。** 道ごとに「読み（ひらがな）」と「別名」を持たせ、「やびつ」「ヤビツ」「ﾔﾋﾞﾂ」のどれでも「ヤビツ峠」が出るようにする。**変換中の文字でも候補を更新する**が、変換中の Enter で候補を選ばない（出典 M1, M2）。
4. **候補を押したら、その道の詳細へ直接行く。** 「検索」キー（Enter）を押したときだけ一覧画面を出す（「スカイライン」のように 52本も当てはまる言葉のため。出典 W1）。
5. **線が伸びる動きは 1.5秒前後・1回だけ・「もう一度なぞる」ボタンつき。** 動きを減らす設定の人には、最初から全部描いた線を出す（出典 W3, M4）。
6. **お気に入りは「♡ お気に入り」（記号＋文字）のボタン1つ。** 外すときは確認を出さず、トーストの「元に戻す」で戻せるようにする。
7. **お気に入り → 走った記録** は、お気に入りの道の詳細の下の主ボタン「＋ 走った記録を追加」でつなぐ（今の DS 5-4 と同じ形）。
8. 安全: 検索もお気に入りも「家で計画するときの機能」として作る。**現在地・近くの道・所要時間・速度は出さない**（PRD 4.3 を守る）。

一番大きな未決事項は **道のデータ（名前・読み・線の形）をどこから持ってくるか**（9章 Q1）。線の形のデータがないと「なぞる動き」が作れない。

## 1. 競合・参考プロダクトの分析

注意: 今回の調査では Web 検索が使えなかった（回数の上限）。各サービスのヘルプページを直接読んだ範囲で書き、読めなかったところは【未確認】とした。

| プロダクト | 強み | 弱み（このアプリから見て） |
|---|---|---|
| **Google マップ**（場所の保存） | 【事実】場所を開いて「保存」を押し、リストを選んで保存する。1つのリストに 3,000 か所まで（出典 C1）。名前で探す→保存、の流れが多くの人に慣れている【推論】 | 【事実】保存には Google アカウントへのログインが要る（出典 C1）。【推論】「道」ではなく「点（場所）」が中心で、峠道やスカイラインの“線”として保存・評価する形ではない |
| **Apple マップ**（ガイド） | 【事実】場所にメモを付けたり、自分で「ガイド」を作って場所をまとめられる（出典 C2） | 【未確認】ヘルプからは検索欄の候補の出し方の詳細が読めなかった。【推論】Google マップと同じく、道を線として集める作りではない |
| **NAVITIME ドライブ** | 【事実】出発地・到着地の検索欄がページの一番上。経由地を決めて「ドライブコース作成」ができる。都道府県から探せる（出典 C3） | 【事実】画面の一番上は「渋滞考慮」など、移動の時間に関わる選択肢（出典 C3）。【推論】「名前のついた道を集める」目的には入力項目が多い |
| **Strava（ルート）** | 【事実】ルートを「My Routes に保存」でき、公開・非公開を選べる。地図で人気の道（ヒートマップ）が見える（出典 C4） | 【事実】ヘルプに「お気に入り（星）」の説明はない（出典 C4）。【推論】運動の記録・区間のタイムが中心の文化で、このアプリの「速度・タイムを扱わない」と合わない |
| **Wikipedia の道の一覧**（データの参考） | 【事実】「スカイライン」という名前の道だけで 52 本ある（津軽岩木スカイライン〜バンナスカイライン。出典 W1）。【事実】ヤビツ峠の読みは「ヤビツとうげ」、神奈川県秦野市、神奈川県道70号（出典 W2） | 【推論】名前に同じ言葉が多く、「スカイライン」だけでは1本に決まらない → 候補に**都道府県を必ず添える**必要がある。【推論】「箱根スカイライン」と「芦ノ湖スカイライン」のように近くて似た名前もある |

**ここから分かること**【推論】
- 「名前で探す → 保存」の形は、地図アプリで多くの人がすでに慣れている。わざわざ説明しなくても分かる形にできる。
- 他のサービスは「点」か「自分で作るコース」が中心。**「名前のついた道を線で見て、集める」こと自体が、このアプリの見せ場になる**（CEO の「なぞる動き」はこれに合う）。
- ログインなしで保存できるのは、Google マップとの違いとして分かりやすい。

## 2. 調べたこと（項目ごと）

### 2-1. ホームを「検索が先」にする

- 【事実】NN/g は、ホームの検索は「リンクではなく入力欄」にし、ページの上の方に、よくある言葉が収まる幅で置くようにすすめている。リンクを入力欄に変えたら検索の利用が 91% 増えた（出典 N1）。
- 【事実】NN/g によると、人は平均2語ほどの短い言葉で検索し、細かい条件（詳細検索）はホームに置かない方がよい（出典 N1）。
- 【事実】Material 3 は「検索バーは、検索がアプリの主な目的のときにすすめる」としている（出典 G1）。今回は検索が主機能なので当てはまる。
- 【推論】DS v2 の原則「主な操作は画面の一番下に1つ」との関係: 検索欄は文字を打つ部品なので、キーボードが下から出ると下の方は隠れる。**検索欄は上に置き、押すと検索の全画面（検索だけの画面）に切り替わる**形にする。Material 3 の「検索バー → 広がった検索の画面」と同じ考え（出典 G1）。下の主ボタンのバーは、ホームでは置かない（主な操作＝検索欄が一番目立つ場所にあるため）。

### 2-2. 候補（オートコンプリート）の出し方

| 決めること | 提案 | 根拠 |
|---|---|---|
| 候補を出し始める文字数 | **1文字から** | 【推論】日本語は1文字（例:「峠」「伊」）でも意味がある。道のリストは数百〜数千件で端末の中で探すので、1文字でも速い。件数は下の上限で抑える |
| 待ち時間（打ち終わりを待つ時間） | **待たない（打つたびに更新）**。もし遅い端末で重ければ 100ms 程度待つ | 【推論】サーバーに問い合わせないので、待つ理由（通信を減らす）がない。待つと「反応が遅い」と感じさせる |
| 件数 | **最大 6件**。それ以上あるときは一番下に「『スカイライン』の道をすべて見る（52件）」の行 | 【事実】Baymard はスマホで 4〜8件、パソコンで最大10件をすすめる。多くの人は最初の数件から選ぶ（出典 B1）。【推論】390px の画面ではキーボードが半分を使うので、6件で一覧が収まる |
| 一覧の中のスクロール | **一覧の中だけのスクロールを作らない** | 【事実】Baymard は候補の中のスクロールバーは多くの操作の問題を起こすので無くすべき、としている（出典 B1） |
| 1行の中身 | 種類の記号（色の面）＋**道の名前**＋**都道府県**＋種類の名前 | 【事実】Wikipedia の一覧で「スカイライン」が 52本（出典 W1）。【推論】同じ言葉の道が多いので、都道府県がないと選べない |
| 打った文字の目立たせ方 | 名前の中で**打った文字と合った部分を太字**にする | 【事実】NN/g: 言葉の途中でも合う候補を出すときは、打った文字の方を目立たせる（出典 N2）。Baymard は「打った後に続く部分を太字」とする（出典 B1）が、これは先頭から合う場合の話。今回は「西伊豆**スカイライン**」のように途中で合うことが多いので NN/g の方に合わせる【推論】 |
| かなで打って漢字の名前に合ったとき | 太字にできる部分がないので、太字にしない。代わりに名前の下に**読み**を小さく出す（例: 碓氷峠／うすいとうげ） | 【推論】「なぜこの候補が出たのか」が分かるようにする |
| 候補がゼロのとき | 一覧の場所に「『○○』に合う道はありません」＋次にできること（3章のワイヤー 5-3） | 【事実】NN/g: 結果がないことをはっきり伝え、言い換えの案・つづりの直し・**打った言葉を残した検索欄**を出す。冗談は使わない（出典 N3） |
| 最近の検索 | **入力欄が空のとき**だけ、「最近見た道」を最大5件出す（端末の中に保存、1件ずつ消せる・全部消せる） | 【推論】このアプリでは「同じ道をもう一度見る」ことが多いと考えられる。Baymard の検索履歴の記事は本文を取得できなかった【未確認】 |
| 候補を選ぶ前の中身 | 候補は**本当に結果がある言葉だけ** | 【事実】NN/g: 結果がない・関係ない候補は、候補がないより悪い（出典 N2） |

**打ち間違い・表記ゆれへの強さ（いちばん大事）**

日本語では「打ち間違い」より「**書き方の違い**」が問題になりやすい【推論】。次を全部「同じ」として扱う:

| ゆれ | 例 | どう合わせるか |
|---|---|---|
| ひらがな／カタカナ | やびつ ↔ ヤビツ | 探す前に、打った文字も道のデータもカタカナ→ひらがなにそろえる【推論】 |
| 全角／半角 | ﾔﾋﾞﾂ ↔ ヤビツ、ＳＫＹ ↔ SKY | 【事実】JavaScript の `normalize("NFKC")` は「見た目が違うだけで同じ文字」を同じ形にそろえる（出典 M3） |
| かな ↔ 漢字 | うすい ↔ 碓氷峠 | 道ごとに**読み（ひらがな）**を持たせ、読みでも探す【推論】。漢字を自動で読みに変える仕組みはブラウザにない（ので、データ側に読みが必要） |
| 「峠」「とうげ」のあるなし | ヤビツ ↔ ヤビツ峠 | 名前の**途中から**でも合うようにする（先頭からだけにしない） |
| 別名・旧名 | 箱根スカイライン ↔ 芦ノ湖スカイライン は**別の道**（出典 W1）。一方、通称と正式名が違う道もある | 道ごとに「別名」を持たせる【推論】。別名で合ったときは「別名: ○○」と小さく出す |
| 空白・中黒・長音 | 「西伊豆 スカイライン」「スカイライン」と「スカイライン」 | 空白と中黒（・）は無視してそろえる【推論】 |
| ローマ字 | yabitsu | **MVP では扱わない**（9章 Q4） |

【推論】1文字の打ち間違い（例:「やびす」）まで直すしくみは、短いかなの言葉では関係ない道まで合いやすく、候補の質が下がる（NN/g「関係ない候補は悪い」出典 N2）。**MVP では入れず、ゼロ件のときの案内で補う**。

### 2-3. 日本語入力（IME）で気をつけること

- 【事実】IME で変換している間も、入力のイベントは届く。`InputEvent.isComposing` は「変換の始まり（compositionstart）と終わり（compositionend）の間か」を返す（出典 M2）。
- 【事実】変換中のキー入力（keydown）を無視するには `event.isComposing || event.keyCode === 229` を両方見る。変換の始まり・終わりの合図とキー入力の順番が前後することがあるため（出典 M1）。
- 提案:
  1. **変換中も候補を更新する**。変換前の「やびつ」（下線つき）で、読みの合う「ヤビツ峠」を出す【推論】。スマホのかな入力では、確定する前に候補を見たい人が多いと考えられる。
  2. **変換中の Enter・↑↓ は IME のもの**。候補を選んだり、検索したりしない（上の出典 M1 の方法で判定）【推論】。これを守らないと「変換を確定しようとしたら勝手に別の道が開いた」になる。
  3. 変換中は、候補の一番上に「打っている文字（例: やびつ）」を出さない。入力欄の中に見えているので重複になる【推論】。
  4. 入力欄の設定: `type="search"`、`enterkeyhint="search"`（キーボードの Enter が「検索」になる。出典 M5）、文字は 16px（iOS の自動拡大を防ぐ。DS 6-9 と同じ）。
- 【未確認】iPhone の Safari・日本語かなキーボード（フリック入力）で、変換中の候補の更新と Enter の扱いが上のとおり動くかは、**実機で確かめる**必要がある（確かめ方: iPhone で「やびつ」をフリックで打ち、確定前に候補が出るか／確定の Enter で詳細に移らないかを見る）。

### 2-4. 候補を選んだら「詳細へ直接」か「一覧へ」か

| 操作 | 行き先 | 理由 |
|---|---|---|
| 候補の1行を押す | **その道の詳細（なぞる地図つき）へ直接** | 【推論】押した時点で1本に決まっている。一覧を挟むと1手増えるだけ |
| 「検索」キー（Enter）を押す／「○○の道をすべて見る」を押す | **結果の一覧画面** | 【推論】「スカイライン」（52本。出典 W1）のように1本に決まらない言葉のため。一覧は種類チップ・都道府県で絞れる（今のホームの部品を使い回せる） |
| 結果が1件だけで Enter | 一覧を出す（勝手に詳細へ飛ばない） | 【推論】動きを予想できるようにする（Enter はいつも一覧） |

一覧の並び順（現在地は使わない）【推論】: ①名前が打った文字で**始まる**道 ②名前の途中に含む道 ③読み・別名で合った道。同じ段の中は**都道府県の北から**（DS の都道府県の並びと同じ）。

### 2-5. 地図と「なぞる」動き

- 【事実】SVG の線は `stroke-dashoffset` を動かすことで「線が描かれていく」見た目を CSS だけで作れる。主なブラウザで2017年から使える（出典 M6）。
- 【事実】NN/g は画面の部品の動きを 100〜500ms にすすめ、500ms を超えると「待たされている」と感じやすいとする（出典 N4）。
- 【事実】WCAG 2.2.2: 自動で始まり、**5秒を超えて**、ほかの内容と同時に出る動きには、止める手段が要る（出典 W4）。
- 【事実】WCAG 2.3.3（AAA）: 操作がきっかけの動きは、止められるようにする。`prefers-reduced-motion` に合わせるのが十分な方法の1つ（出典 W3）。iPhone は「設定 > アクセシビリティ > 動作」で設定する（出典 M4）。

提案:
| 決めること | 提案 | 理由 |
|---|---|---|
| 動く時間 | **約 1.5秒**（道の長さにかかわらず 1.2〜2.0秒の間に収める） | 【推論】これは操作への返事ではなく「道の形を見せる」見せ場なので、NN/g の 500ms より長くてよい。ただし 5秒（W4）よりずっと短くして、止めるボタンなしでも待てる長さにする |
| 動きの順番 | ①地図（県の形と海岸線など）を先に出す → ②**始まりの点**を出す → ③線が始まりから終わりへ伸びる → ④終わりに点 | 【推論】「どこから、どこへ」が分かる |
| 何回動くか | **画面を開いたとき1回だけ**。くり返さない | 【推論】ずっと動くと文字を読むじゃまになる（DS 4-7「見せ場は1つ」と同じ考え） |
| もう一度 | 地図の左下に「↻ もう一度なぞる」（文字つき、44px） | 【推論】見逃した人のため。押したときだけ動くので W3 の「操作がきっかけの動き」にあたる |
| 動きを減らす設定 | **最初から全部描いた線**を出す。「もう一度なぞる」ボタンは出さない | 出典 W3, M4 |
| 線の色・太さ | 道の種類の solid 色、太さ 5px、端は丸。下に白い 2px のふち（地図の上で見えるように） | DS 4-2（種類の色）を使う |
| 地図の拡大 | 道全体が入る大きさで固定。指で動かさない | 今の DS 6-12「詳細の地図は表示だけ」と同じ |
| 出典の表示 | 地図の**右下**、隠さない。地理院タイルを使うなら「地理院タイル」＋一覧ページへのリンク | 【事実】地理院タイルは「国土地理院」または「地理院タイル」等と書き、一覧ページへリンクを付けることが求められている（出典 G2）。【事実】OpenStreetMap のデータを使うなら、OpenStreetMap への謝辞とライセンス（ODbL）を示す必要があり、地図の隅に出す例が示されている（出典 O1）。簡単な SVG でも、**元にしたデータの出典は必要**【推論】 |
| 読み上げ | 地図は `role="img"`、名前は「ヤビツ峠の道の形。神奈川県秦野市」のように文字で | 【推論】DS 6-12 は「飾り」扱いだが、今回は道の形が主な情報なので、短い説明を付ける |

### 2-6. お気に入り

| 決めること | 提案 | 理由 |
|---|---|---|
| 記号 | **♡（ハート）＋「お気に入り」の文字** | 【推論】DS で「評価に星を使わない」と決めている（DS 2章「引き継ぐもの」）。星をお気に入りに使うと評価と混ざる。文字を必ず付けるのは DS の原則（記号だけにしない） |
| 置き場所 | 道の詳細の**下の主ボタンのバー**に「♡ お気に入りに追加」（まだのとき）。追加した後は、主ボタンが「＋ 走った記録を追加」に変わり、♡ は帯の右上の小さなボタン（「♥ お気に入り」、押すと外す）に移る | 【推論】DS 原則「主な操作は下に1つ」。お気に入りにする前は「お気に入りにする」が一番大事、した後は「記録する」が一番大事 |
| 状態の伝え方 | 塗りつぶしの ♥＋「お気に入り」／ふちだけの ♡＋「お気に入りに追加」。`aria-pressed` | DS「色だけで伝えない」 |
| 外すとき | **確認は出さない**。トースト「お気に入りから外しました ［元に戻す］」 | 【推論】すぐ戻せる操作に確認を出すと手間が増える。ただしトーストは消えるので、戻す方法はトーストだけにしない（詳細でもう一度押せば戻る）。トーストは DS の4秒より長め（8秒前後）にし、フォーカスが入っている間は消さない【推論】 |
| 走った記録がある道を外すとき | **走った記録は消さない**。お気に入りから外れても、ホームの「走った道」に残る | 【推論】「お気に入り」と「走った記録」は別のもの。外しただけで記録が消えると取り返しがつかない（9章 Q3 で CEO に確認） |
| 空の状態 | 「まだお気に入りがありません。上の検索で道を探して、♡ を押すとここに並びます。」＋よく検索される道の例を3つ（押すと詳細へ） | DS 6-11（空の状態は「いまの状態・使い方・次の操作」を伝える。NN/g） |

### 2-7. お気に入りと「走った記録」のつながり

- 今の PRD v2 は「道を登録 → 道詳細 → ＋ 走った記録を追加」の流れ（PRD 6章）。**「道を登録」を「♡ お気に入りに追加」に置き換えれば、その後はそのまま使える**【推論】。
- データの考え方【推論】: 道のリスト（アプリに入っている、だれでも同じもの）と、自分の記録（端末の中、書き出しの対象）を分ける。自分の側には「お気に入りにした道の ID と日時」と「走った記録」だけを持つ。今の Road（自分で名前を打つ道）は「リストにない道を自分で足す」として残すかどうかを決める（9章 Q2）。
- 書き出し（JSON）にはお気に入りも入れる（端末を変えたときに消えないように）【推論】。

### 2-8. 安全

- 【推論】検索・お気に入りは「家や休憩中に、次に行く道を決める」ときの機能。運転中に使う場面を作らないため:
  - **現在地・「近くの道」・道案内（ナビ）は作らない**（PRD 4.3 で位置情報の取得はずっと扱わないと決まっている）。
  - 道の詳細に**所要時間・速度・タイムを出さない**（PRD 4.3）。道の長さ（km）を出すかは 9章 Q5。
  - 線が伸びる動きは「走っている車」を思わせない: 車やバイクの絵・矢印・速さを表す線は使わない（DS 6-11 の「描かない物」と同じ）。線は「地図に色を塗っていく」見た目にする。
  - はじめての案内（2ステップ）の安全の約束はそのまま残す。

## 3. おすすめの流れ（ホーム → 打つ → 候補 → 道の詳細 → お気に入り → 走った記録）

**ゴール**: 初めての人が、1分以内に「行ってみたい道を見つけて、お気に入りにする」。
→ **そのために** ホームを開いた瞬間に検索欄が目に入り、押せばすぐ打てる。
→ **さらにそのために** 打った1文字目から候補が出て、押せば道の形が見える（なぞる動き）。
→ **その先で** お気に入りにした道を、走った後に開いて記録を残す。

```
[ホーム]
  │ 検索欄を押す
  ▼
[検索の全画面]  入力欄が空 → 「最近見た道」（なければ「例: ヤビツ峠」）
  │ 「やびつ」と打つ（変換中でも候補が出る）
  ▼
[候補 最大6件] ──── 候補ゼロ ──→ [ゼロ件の案内]（打ち直し・種類から探す）
  │            └─ Enter（検索キー）→ [結果の一覧]（種類・都道府県で絞る）─┐
  │ 候補を押す                                                          │ 押す
  ▼                                                                     ▼
[道の詳細]  地図 → 始まりの点 → 線が伸びる（約1.5秒・1回）→ 終わりの点
  │ 下の主ボタン「♡ お気に入りに追加」
  ▼
[道の詳細（お気に入り済み）] トースト「お気に入りに追加しました」
  │ 下の主ボタンが「＋ 走った記録を追加」に変わる
  │ （走った後、ホームの「お気に入り」から開く）
  ▼
[走った記録の追加]（今の DS 5-5 のまま。安全バナーつき）
  │ 保存
  ▼
[道の詳細] 評価のまとめ・記録が増える
```

分かれ道:
- **すでにお気に入りの道を候補で選んだ**: 詳細の主ボタンは最初から「＋ 走った記録を追加」。
- **地図のデータ（線）がない道**: 地図の場所に「この道の形のデータはまだありません」＋都道府県名。お気に入りと記録はできる。
- **地図が読み込めない（電波がない）**: 簡単な SVG を端末の中のデータで描くなら、電波がなくても線は出せる【推論】（地図の画像タイルを使うと出せない。9章 Q1 と関係）。

## 5. アクセシビリティ（だれでも使えるようにする）

### 5-1. 検索欄と候補の作り（WAI-ARIA のコンボボックス）

【事実】W3C の「WAI-ARIA Authoring Practices（作り方の手本集）」のコンボボックスの決まり（出典 A1, A2）:

| 部品 | 付けるもの |
|---|---|
| 入力欄 | `role="combobox"`、`aria-expanded`（候補が出ていれば true、出ていなければ false）、`aria-controls`（候補の一覧の id）、`aria-autocomplete="list"`（入力欄の文字は勝手に書き換えず、一覧で候補を出す）、見える文字のラベル（「道の名前で探す」） |
| 候補の一覧 | `role="listbox"`、各行 `role="option"` |
| 選ばれている行 | 入力欄の `aria-activedescendant` に、その行の id を入れる。**フォーカス（キーボードの位置）は入力欄に置いたまま**（出典 A1） |

キーボード（出典 A1, A2）:
| キー | 動き |
|---|---|
| ↓ | 候補の一覧の最初へ（目で見える選択が移る） |
| ↑ | 一覧の最後へ（任意） |
| Enter | 候補が選ばれていれば、その道の詳細へ。選ばれていなければ結果の一覧へ（2-4） |
| Esc | 候補が出ていれば閉じる。出ていなければ入力欄を空にする |
| Alt＋↓ | 選択を動かさずに一覧を開く（任意） |

- 【事実】`aria-activedescendant` で指した行は、ブラウザが自動で画面内にスクロールしないので、プログラムで見える位置に動かす必要がある（出典 A2）。
- **変換中（IME）は ↑↓・Enter を受け取らない**（2-3。出典 M1）。
- 【未確認】iPhone の VoiceOver は、`aria-activedescendant` で選んだ候補を正しく読まないことがあると言われている。実機で確かめる（確かめ方: VoiceOver をオンにして、候補を指でなぞって選べるか、件数が読まれるか）。指で各行を直接押せるので、選べなくなることはない【推論】。

### 5-2. 読み上げで知らせること

【事実】WCAG 4.1.3: 「18件見つかりました」「見つかりませんでした」のような**件数・状態の短い文**は、フォーカスを動かさずに読み上げで伝わるようにする（`role="status"` など）。結果の一覧そのものは知らせる対象ではない（出典 W5）。

| いつ | 読む文（例） | 付け方 |
|---|---|---|
| 候補が変わったとき | 「候補 6件。上下の矢印で選べます」／「候補 1件」 | 一覧の外に置いた `role="status"`。打つたびに読ませるとうるさいので、**打ち終わってから 500ms 程度後**に1回【推論】 |
| ゼロ件 | 「『やびす』に合う道はありません」 | 同上 |
| 結果の一覧 | 「『スカイライン』 52件」 | 同上 |
| お気に入りの追加・外す | 「お気に入りに追加しました」／「お気に入りから外しました。元に戻すボタンがあります」 | トースト `role="status"` |
| なぞる動き | 読まない（動きは目で見るもの）。地図の説明文で道の形を伝える | 地図に `role="img"` と名前 |

### 5-3. フォーカス（キーボードの位置）

- ホームの検索欄を押す → 検索の全画面で、**入力欄にフォーカス**。戻る［‹］でホームに戻ると、フォーカスは**ホームの検索欄**に戻る【推論】。
- 候補を押して詳細へ → フォーカスは詳細の見出し（道の名前）へ。戻ると、検索の全画面に**打った言葉を残したまま**戻る【推論】。
- お気に入りの♥ボタンは `button` ＋ `aria-pressed`。押しても見出しは変えず、フォーカスはボタンに残す。主ボタンが「＋ 走った記録を追加」に変わるときは、変わったことをトーストで知らせる【推論】。
- 固定の上下のバーでフォーカスが隠れないようにする（今の DS 6 章の `scroll-padding` をそのまま使う）。

### 5-4. そのほか

- 候補の1行は高さ 56px（押せる範囲 44px 以上。DS 4-5）。［×］［‹］も 44px。
- 合った部分の目立たせ方は**太字**（色だけにしない。DS「色だけで伝えない」）。
- 種類の色の記号には、必ず種類の名前を添える（DS 4-2）。
- 線の色と地図の色のコントラストは 3:1 以上（部品の基準。DS 4-3 と同じ考え）。白いふちを付けて、淡い地図の上でも見えるようにする。

## 6. このアプリで大事にする UX の原則（5つ）

1. **打った瞬間に、合う道が見える。** 端末の中で探すので待ち時間がない。サーバーに打った文字を送らない（v2 の「データは端末の中だけ」）。
2. **書き方が違っても見つかる。** ひらがな・カタカナ・半角・漢字の読み・別名を同じに扱う。「スペルを正しく打つ」責任を利用者に負わせない。
3. **候補を押したら1歩で道の形まで。** 一覧を挟むのは、1本に決まらない言葉のときだけ。
4. **動きは「道の形を伝える」ためだけに、1回だけ。** 繰り返さない。止めたい人（動きを減らす設定）には最初から描いた線。
5. **探すのは家で、記録は走った後で。** 現在地・近くの道・時間・速度は出さない。
