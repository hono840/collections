## 0. 計算ロジック仕様（実装の唯一の正）

本章の数式・丸め・単位・閾値は、実装・テスト・コピーすべての「唯一の正」とする。これに反する挙動は不具合として扱う。以降の機能仕様は本章を参照する。

### 0.1 用語と基本方針

| 用語 | 意味 |
| --- | --- |
| 購入価格 | ある食材を1回に購入した金額（**内部保存は常に税抜に正規化**） |
| 購入量 | その金額で購入した数量（例: 1000g、1L、1個） |
| 歩留まり率 (yield %) | 購入量のうち実際に使用可能な割合（1〜100%）。廃棄・下処理ロスを表す |
| 有効単価 | 使用可能量あたりの単価（税抜）。原価計算の基礎値 |
| 原価 | 1メニューを1食提供するのにかかる食材費合計（税抜） |
| 売価 | メニューの販売価格（内部保存は税抜に正規化。表示は税込/税抜切替可） |
| 原価率 | 売価に対する原価の割合。**低いほど良い**（利益が大きい） |
| 粗利 | 売価から原価を引いた利益（税抜） |

### 0.2 コア数式（実装にそのまま渡せる粒度）

```
# 有効単価（使用可能量ベース、税抜）
有効単価 = 購入価格(税抜) ÷ ( 購入量 × (歩留まり率 / 100) )

# メニュー原価（税抜）
原価 = Σ ( 各材料の有効単価(税抜) × 使用量[食材の基準単位に換算後] )

# 原価率（%）
原価率 = 原価(税抜) ÷ 売価(税抜) × 100

# 粗利（税抜）
粗利 = 売価(税抜) − 原価(税抜)

# 値上げシミュレーション: 目標原価率 r% から推奨売価を逆算（税抜）
推奨売価(税抜) = 原価(税抜) ÷ ( r / 100 )
```

**検証例（キャベツ）**: 購入価格 ¥200（税抜）、購入量 1000g、歩留まり 80% → 有効単価 = 200 ÷ (1000 × 0.80) = 200 ÷ 800 = **¥0.25/g**。使用量 80g なら材料費 = 0.25 × 80 = **¥20**。

### 0.3 消費税の扱い（最もシンプルかつ正しい定義）

- **内部保存は常に税抜に正規化する。** 原価率・原価・粗利はすべて税抜同士で算出する（`原価率 = 税抜原価 ÷ 税抜売価 × 100`）。税抜同士で比較することで原価率の意味が一貫する。
- **入力時に「税込／税抜」トグル ＋ 税率**を持つ。税込入力の場合は次式で税抜へ換算して保存する。

```
税抜金額 = 税込金額 ÷ ( 1 + 税率 / 100 )
```

- **既定税率**:
  - 食材（購入価格）の既定 = **8%（軽減税率）**。10% も選択可（酒類・外食仕入等）。
  - 売価の既定 = **10%（標準税率・店内飲食）**。8% も選択可（テイクアウト主体の店）。
- **既定入力方式**: 食材は「税込」入力を既定とする（仕入伝票が税込表記のことが多いため）。売価は「税込」入力を既定とする（メニュー表は総額表示義務により税込表記が一般的なため）。両者ともグローバル設定で既定を変更でき、各入力欄でも個別に切り替えられる。
- **過剰設計をしない**: 明細行ごとに複数税率を混在管理はしない。8%軽減／10%は「入力換算」と「表示ラベル」のレベルにとどめる。
- **売価表示**: メニューには税抜売価と税込売価の両方を表示する（オーナーがメニュー表に載せるのは税込のため）。原価率の分母は常に税抜売価。

### 0.4 単位と換算（次元の一致）

食材の購入単位と、レシピでの使用量の単位は**同一次元でなければならない**。次元をまたぐ指定（例: 個で買った食材をgで使う）は不可。

| 次元 | 単位 | 基準単位（計算内部） | 換算則 |
| --- | --- | --- | --- |
| 重量 | kg, g | g | 1 kg = 1000 g |
| 容量 | L, ml | ml | 1 L = 1000 ml |
| 個数 | 個 / 枚 / 束 / 本 / 袋 / 玉 / 丁 など | 各単位そのもの | **換算なし。同一単位のみ相互利用可** |

- 重量・容量は同次元内で自動換算する（kg↔g、L↔ml）。
- 個数系の単位は**互いに換算不可**（個 ≠ 枚 ≠ 束）。個数で登録した食材は、レシピでも**同一の個数単位**でしか使用量を指定できない。
- **設計上の防止**: レシピの使用量の単位セレクタは、選択中の食材の購入単位と互換な単位のみを表示する（重量食材→{kg, g}、容量食材→{L, ml}、個数食材→その単位のみ）。これにより非互換な入力を構造的に防ぐ。
- **玉・束などでg単位計算したい場合の運用**: 「キャベツ 1玉」を g 単位で使いたいときは、食材登録時に購入量を重量で入力する（例: 購入価格 ¥200・購入量 1000g）。この場合レシピはgで指定できる。個数（1玉）で登録した場合はレシピも玉（例: 0.3玉）で指定する。どちらも正しい。

### 0.5 丸めと精度（実装にそのまま渡せる方針）

- **内部計算はフル精度**（倍精度浮動小数）で行い、**丸めは表示時のみ**行う。原価は「各材料費をフル精度で合計 → 合計を表示時に丸め」とし、行ごとに丸めてから合計しない（丸め誤差の累積を避ける）。
- **表示丸め**:
  - 金額（原価・売価・粗利など、円）: 表示時に**四捨五入で整数**。
  - 有効単価: 表示時に**小数第2位**まで（例: ¥0.25/g）。
  - 原価率: 表示時に**小数第1位**まで（例: 32.5%）。**色分け判定も、この小数第1位に丸めた値で行う**（表示値と色が一致するように）。
- **税抜換算**: `税込 ÷ (1 + 税率/100)` はフル精度で保持し、表示時のみ丸める。
- **値上げシミュの推奨売価丸め**: 推奨売価(税抜) を算出後、**丸め単位（既定 ¥10、設定で ¥1／¥10／¥50／¥100 から選択可）で切り上げ (ceil)** する。切り上げにより実効原価率は必ず目標以下（＝安全側）になる。丸め後は「税込換算額」と「丸め後の実効原価率」を再表示する。

### 0.6 原価率アラートの閾値（既定・ユーザー変更可）

原価率は低いほど良い。信号色は次のとおり。**閾値は設定画面でユーザーが変更できる。**

| 色 | 意味 | 既定条件 |
| --- | --- | --- |
| 緑 | 良好 | 原価率 < 注意閾値（既定 **30%**） |
| 黄 | 注意 | 注意閾値 ≤ 原価率 ≤ 危険閾値（既定 **30〜35%**） |
| 赤 | 危険 | 原価率 > 危険閾値（既定 **35%**） |

- 境界の厳密定義: `原価率 < 注意閾値` → 緑 / `注意閾値 ≤ 原価率 ≤ 危険閾値` → 黄 / `原価率 > 危険閾値` → 赤。判定は 0.5 の丸め済み原価率で行う（例: 危険閾値35 のとき 35.0%=黄、35.1%=赤）。
- 設定制約: 注意閾値 < 危険閾値 を必須とする（逆転・同値は保存不可でインラインエラー）。
- 色のみに依存しない: 各バッジには色に加えて**テキストラベル（良好／注意／危険）**を必ず併記する（アクセシビリティ・印刷対応）。

## 1. 概要・ゴール・非ゴール

### 1.1 1行のプロダクト定義

**「食材の仕入れ値を1つ直すだけで、それを使う全メニューの原価率が即座に再計算される、POS不要・登録不要・ブラウザ完結の個人店向け原価計算ツール。」**

### 1.2 対象ユーザー

個人経営の飲食店オーナーシェフ／店主（30〜50代、居酒屋・カフェ・ラーメン・定食・バル系を1〜3店舗運営）。POS未導入または原価管理機能のない簡易POS利用。原価はExcelか勘。円安・物価高で仕入れ値が毎月動くが、赤字メニューの特定と適正な値上げ額の算出を放置しがち。加えて開業準備層（事業計画で原価率を詰める層）をセカンダリに置く。詳細は第2章。

### 1.3 ゴール（成功指標の考え方）

計装（GA4）は外部送信最小の範囲で導入するが、プライバシー約束（レシピ・仕入価格は端末外に出さない）に反する計測は行わない。北極星は「反復利用によるProサブスク継続」。

| 指標カテゴリ | 指標（考え方） |
| --- | --- |
| アクティベーション | 初回訪問者のうち「サンプルで即時再計算(wedge)を体験」→「自分の食材を1件登録 または 自分のメニューを1件作成」に到達した割合 |
| wedge到達 | 食材価格の編集を1回以上行い、メニューの原価率が更新されるのを見たセッション割合 |
| 無料→Pro転換 | 3メニュー上限への到達数、料金ページ表示数、Proライセンスキー解錠数 |
| リテンション（最重要） | 2回目以降の訪問で「食材価格を更新」したユーザー割合（＝反復価値・チャーン抑制の先行指標） |
| 事業KPI | 有料 306件（¥980/月換算）で月商30万円（財務ブリーフ参照）。制約は市場規模でなく獲得スループット |

### 1.4 非ゴール（このリリースで狙わないこと）

- リアルタイムのライブ市況（食材相場API）連携による自動価格更新。
- 会計・確定申告・インボイス発行の代替。
- 複数店舗の横断集計・スタッフ管理・人件費を含むFL全体最適。
- クラウド同期・アカウント（端末をまたいだ自動同期はJSONバックアップで代替）。

詳細なスコープ外は第7章。

## 3. ユーザーストーリー

「〜として、〜したい、なぜなら〜」形式。主要フロー順に記載する。

### 3.1 初回オンボーディング

- オーナーとして、**初回起動時にサンプルの食材とメニューが入った状態で始めたい**。なぜなら、白紙からでは価値が分からず、まず動くものを触りたいから。
- オーナーとして、**サンプルの食材価格を変えて全メニューの原価率が動くのを最初に体験したい**。なぜなら、このツールの核心価値（即時再計算）を最短で理解したいから。
- オーナーとして、**サンプルを一括で削除して自分のデータで始められるようにしたい**。なぜなら、他人のサンプルが残っていると邪魔だから。

### 3.2 食材登録

- オーナーとして、**食材名・購入価格・購入量・単位・歩留まり率を登録したい**。なぜなら、これが全メニューの原価計算の土台だから。
- オーナーとして、**仕入伝票どおり税込のまま金額を入力したい**（税抜換算はツールに任せたい）。なぜなら、伝票の数字をそのまま打ちたいから。
- オーナーとして、**入力した瞬間に有効単価（使える量あたりの単価）が自動で出てほしい**。なぜなら、歩留まりを考えた本当のコストを知りたいから。

### 3.3 メニュー（レシピ）作成

- オーナーとして、**メニュー名・売価・材料（食材＋使用量）を登録したい**。なぜなら、1品ごとの原価・原価率・粗利を知りたいから。
- オーナーとして、**登録した材料から原価・原価率・粗利が自動計算されてほしい**。なぜなら、電卓・Excelの手計算をやめたいから。
- オーナーとして、**原価率の高い順にメニューを並べて見たい**。なぜなら、危険なメニューから手を打ちたいから。

### 3.4 価格変更で全再計算を体験（THE WEDGE）

- オーナーとして、**ある食材の価格を1つ更新するだけで、その食材を使う全メニューの原価率が即座に再計算されてほしい**。なぜなら、仕入れが上がるたびに全メニューを手計算し直すのは非現実的だから。
- オーナーとして、**再計算の結果、危険域に落ちたメニューが赤く目立ってほしい**。なぜなら、対応すべきメニューを見逃したくないから。

### 3.5 値上げシミュレーション

- オーナーとして、**「原価率30%にするには何円？」を1品ごとに知りたい**。なぜなら、勘でなく根拠を持って値付けしたいから。
- オーナー（Pro）として、**目標原価率を全メニューに一括で当てて、それぞれの推奨売価を一覧で見たい**。なぜなら、値上げ時期に全メニューをまとめて見直したいから。

### 3.6 エクスポート／バックアップ

- オーナーとして、**データをJSONでバックアップし、後で復元したい**。なぜなら、localStorageはブラウザ操作で消えることがあり、営業秘密を自分で守りたいから。
- オーナー（Pro）として、**メニュー一覧や原価計算書をCSV／PDFで出力したい**。なぜなら、Excelで加工したり、印刷して厨房に貼ったり、税理士に渡したいから。

### 3.7 Pro解錠

- オーナーとして、**メニューが3件を超えたら、分かりやすくProへの案内を受けたい**。なぜなら、なぜ追加できないのか理由と対処を知りたいから。
- オーナーとして、**購入後に届いたライセンスキーを入力するだけでProが解錠されてほしい**。なぜなら、面倒なログインをしたくないから。
- オーナーとして、**同じキーを厨房のタブレットとスマホの両方で使いたい**。なぜなら、同じ店で複数端末を使うから。

### 4.a 食材マスタ

#### 概要
食材ごとに購入価格・購入量・単位・歩留まり率を登録し、有効単価（税抜）を自動導出する。全メニューの原価計算の基礎データ。**Free/Pro とも登録数は無制限**（3メニューを作るのに材料は必要なため）。

#### ユーザーインタラクション
1. 「食材を追加」→ 入力フォーム（食材名 / 購入価格 ＋ 税込・税抜トグル ＋ 税率 / 購入量 / 単位 / 歩留まり率）→ 保存 → 一覧に追加され有効単価が表示される。
2. 食材をタップ → 編集 → 各項目を変更 → 保存 → 有効単価が即再計算され、この食材を使う全メニューも再計算される（第4.c参照）。
3. 食材を削除 → 確認 → 削除。この食材を使うメニューがある場合は警告を表示（第8章「食材削除」）。
4. 一覧で食材名の検索・並べ替え（名前順／有効単価順）。

#### 状態
- デフォルト: 食材カードのリスト（名称・購入価格・購入量・単位・歩留まり率・有効単価）。
- ローディング: localStorage 読込は同期的で通常一瞬。破損時は第8章の復旧UI。
- 空: サンプル削除後などで0件のとき「食材を追加して始めましょう」＋追加CTA。
- エラー: 入力バリデーション違反（歩留まり0、購入量0、負値など）をインライン表示。
- 成功: 保存時に有効単価が即時表示。

#### 受入条件
- [ ] Given 食材フォーム、When 食材名・購入価格(税抜)¥200・購入量1000g・歩留まり80%を保存、Then 有効単価が **¥0.25/g** と表示される。

### 4.b メニュー（レシピ）

#### 概要
メニュー名・売価・材料明細（食材＋使用量）を登録し、原価・原価率・粗利を自動計算する。**Free は最大3件**、**Pro は無制限**（第5章）。

#### ユーザーインタラクション
1. 「メニューを追加」→ メニュー名 / 売価（税込・税抜トグル ＋ 税率）を入力 → 材料を追加（食材を選択 → 使用量＋単位を入力）→ 保存。
2. 保存と同時に 原価（税抜）・原価率（%）・粗利（税抜）・信号色バッジが表示される。
3. 材料行の追加・編集・削除ができ、変更のたびに原価・原価率・粗利が即再計算される。
4. メニューを複製（Could。第6章）／削除できる。
5. メニュー詳細から値上げシミュレーション（第4.d）へ遷移できる。

#### 状態
- デフォルト: メニューカード（名称・税込/税抜売価・原価・原価率＋信号色・粗利）。
- 空: 0件のとき「最初のメニューを作りましょう」＋CTA（オンボーディングのサンプル投入導線）。
- エラー / 要確認: 売価0・未設定、または参照食材が削除済みのとき原価率を「—」表示し「要確認」バッジ（第8章）。
- 上限到達（Free）: 3件時に「メニューを追加」でアップセル（第5章）。
- 成功: 計算結果が即時表示。

#### 受入条件
- [ ] Given 有効単価 ¥1.0/g の鶏もも肉、When 使用量150g の材料としてメニューに追加、Then その材料費は ¥150 と計算される。
- [ ] Given 材料費合計（税抜）¥203 のメニュー、売価 税込¥900（税率10%）、When 保存、Then 税抜売価 ¥818（818.18…の表示丸め）、原価率 = 203 ÷ 818.18 × 100 ≒ **24.8%**、粗利（税抜）≒ ¥615 と表示される。
- [ ] Given 原価率24.8%（既定閾値 緑<30）、When メニュー一覧を見る、Then 信号色は緑・ラベル「良好」。
- [ ] Given メニュー編集で材料を1行削除、When 削除、Then 原価・原価率・粗利が即再計算される（保存ボタンや再読込を待たない）。
- [ ] Given Free ユーザーがメニュー3件保有、When 「メニューを追加」をタップ、Then 新規作成されず、アップセルモーダルが表示される（第5章）。
- [ ] Given 売価が未設定のメニュー、When 一覧表示、Then 原価率は「—」・「要確認」バッジが出て、アプリはクラッシュしない（第8章）。
- [ ] Given 材料に使う食材が別画面で削除された、When メニューを開く、Then その材料行に警告バッジが付き、原価は「不明」扱い（誤った原価を出さない、第8章）。

### 4.c THE WEDGE（食材価格変更 → 全メニュー即時再計算）【最重要】

#### 概要
ある食材の購入価格（または購入量・歩留まり率）を変更すると、その食材を使う**全メニューの原価・原価率・粗利・信号色・ダッシュボード順位が即座に再計算される**。本アプリの唯一無二の差別化機能であり、受入条件を最も厳密に定める。

#### 「即座に」の定義（実装・テストの基準）
- **明示的な「再計算」操作・保存ボタン・ページ再読込を要さない。** 変更値が有効な数値として確定した時点（入力確定＝onChange/blur時、望ましくはライブ）で、依存する全メニューの表示が更新されていること。
- 更新対象は「その食材を材料に含む全メニュー」のみ。含まないメニューは変化しない。
- 更新される表示: 原価、原価率（数値＋小数第1位）、粗利、信号色バッジ＋ラベル、ダッシュボードの並び順、上限・要確認バッジ。

#### ユーザーインタラクション
1. 食材の購入価格（or 購入量 or 歩留まり率）を編集し確定。
2. 同一画面上、または遷移先のダッシュボード／メニュー一覧で、該当メニューの原価率等が更新済みで表示される。
3. （任意）変更前後の差分を強調表示（Could。第6章）。

#### 状態
- デフォルト: 通常表示。
- 再計算中: 計算はクライアント内で軽量・同期的に完了する想定（数百メニュー規模でも体感遅延なし）。仮に重い場合もUIをブロックしない。
- エラー: 変更で売価0のメニューが原価率算出不能になる場合は「—」＋要確認（クラッシュしない）。

#### 受入条件
- [ ] Given 食材X を材料に含むメニューM1・M2、含まないメニューM3、When X の購入価格を変更して確定、Then M1・M2 の原価・原価率・粗利が新値で再計算され、**M3 は不変**。かつ再計算に「再計算」ボタン押下や再読込は不要。
- [ ] Given メニューM1 の原価率が既定閾値で緑（<30%）、When Xの価格を上げて M1 の原価率が 36% になる変更を確定、Then M1 の信号色が**赤**・ラベル「危険」に即更新され、ダッシュボードで上位（悪い順）に並び替わる。
- [ ] Given 食材Xの**歩留まり率**を 90%→70% に変更、When 確定、Then Xを使う全メニューの有効単価が上がり、原価・原価率が増加方向へ即再計算される。
- [ ] Given 食材Xの**購入量**を 1000g→500g（同価格）に変更、When 確定、Then 有効単価が2倍になり、Xを使う全メニューの原価率が上昇して即反映される。
- [ ] Given 300件のメニューが存在し多数が食材Xを使用、When Xの価格を変更、Then すべての該当メニューが再計算され、体感的な遅延なく（目安1秒以内）表示が更新される。
- [ ] Given 変更を確定した直後、When 別ページへ遷移せず同画面のメニュー一覧を見る、Then 既に新しい原価率が表示されている（遷移や更新操作を挟まない）。

### 4.d 値上げシミュレーション（単品=Free / 一括適用=Pro）

#### 概要
目標原価率 r% から推奨売価を逆算し、値付けの根拠を与える。**単品シミュレーション（プレビュー＋そのメニューへの適用）は Free**。**目標原価率を全メニューへ一括反映する「一括適用」は Pro**（第5章）。

#### 数式・丸め
第0章。`推奨売価(税抜) = 原価(税抜) ÷ (r/100)` → 丸め単位（既定¥10）で切り上げ → 税込換算・丸め後の実効原価率を表示。

#### ユーザーインタラクション（単品・Free）
1. メニュー詳細 →「値上げシミュ」→ 目標原価率 r%（既定は現在の注意閾値=30% をプリセット）を入力。
2. 推奨売価（税抜／税込）、丸め後の実効原価率、現在売価との差額（値上げ額）、変更前後の粗利をプレビュー表示。
3. 「この売価を適用」→ そのメニューの売価が推奨値に更新される（＝売価の手編集と等価のため Free で可）。適用しなければ元のまま。

#### ユーザーインタラクション（一括・Pro）
1. ダッシュボードまたは設定 →「全メニューに目標原価率を一括適用」→ r% を入力。
2. 全メニュー（または選択したメニュー）について、現在売価→推奨売価、現在原価率→適用後原価率を一覧プレビュー。
3. 「一括適用」→ 対象メニューの売価が一斉に推奨値へ更新される。適用前に必ずプレビューを挟む。
4. Free ユーザーがこの機能に触れた場合はアップセル（第5章）。

#### 状態
- デフォルト: 目標原価率入力欄＋プレビュー。
- エラー: r ≤ 0 または未入力 → 「目標原価率は0より大きい値」でブロック（ゼロ除算防止）。原価が算出不能（要確認メニュー）なら推奨売価は「—」でスキップ理由を表示。
- 成功: プレビュー→適用完了トースト。適用後は第4.c により関連表示が更新済み。

#### 受入条件
- [ ] Given 原価(税抜)¥203 のメニュー、目標原価率 30%、When 単品シミュを実行、Then 推奨売価(税抜) = 203 ÷ 0.30 = 676.67 → **切り上げ¥680**（既定丸め¥10）、税込10%換算 ¥748、実効原価率 = 203÷680×100 ≒ 29.9%（目標以下）と表示される。
- [ ] Given 丸め単位を¥50に設定、When 同条件でシミュ、Then 推奨売価(税抜)は676.67の切り上げで **¥700**、実効原価率 ≒ 29.0%。
- [ ] Given 単品シミュのプレビュー、When 「この売価を適用」、Then そのメニューの売価が推奨値に更新され、原価率が実効値に変わる（Free で可能）。
- [ ] Given Free ユーザー、When 「全メニューに一括適用」を開く、Then 実行できずアップセルモーダルが出る。
- [ ] Given Pro ユーザーがメニュー5件保有、目標原価率28%、When 一括適用のプレビュー→実行、Then 5件すべての売価が各原価に応じた推奨値へ更新され、各原価率が28%以下になる。
- [ ] Given 目標原価率に 0 を入力、When 実行、Then ゼロ除算せず「0より大きい値を入力」エラー。
- [ ] Given 売価未設定で原価は算出可能なメニューを含む一括適用、When 実行、Then そのメニューは原価から推奨売価を算出して更新できる（原価が算出可能なら対象、原価も不明な要確認メニューはスキップし理由表示）。

### 4.e 原価率アラート（信号色＋ダッシュボード）

#### 概要
原価率を信号色（緑/黄/赤）＋テキストラベルで可視化し、ダッシュボードでは**原価率が悪い（高い）順**に並べて危険メニューを先頭に集める。閾値はユーザー設定可（第0.6章）。

#### ユーザーインタラクション
1. ダッシュボード（ホーム）で全メニューを原価率の悪い順に一覧。
2. 各メニューに信号色バッジ＋ラベル＋原価率＋粗利。
3. 設定で注意閾値・危険閾値を変更 → 全メニューの色が即再判定される。
4. 要確認メニュー（売価未設定・参照食材欠落）は最上部に別枠で提示。

#### 状態
- デフォルト: 悪い順ソートのリスト。
- 空: メニュー0件のとき案内。
- エラー / 要確認: 算出不能メニューを先頭グループに「要確認」で表示。
- 成功: 閾値変更・価格変更に応じて色・順位が更新。

#### ソート仕様（厳密）
ダッシュボードの並び順は次の順:
1. **要確認メニュー**（原価率が算出不能: 売価未設定/0、または参照食材欠落）を最上部（注意喚起）。
2. その下に**原価率の降順**（高い＝悪い順）。同率はメニュー名の昇順。

#### 受入条件
- [ ] Given メニューA=38%・B=32%・C=25%、When ダッシュボードを見る、Then 並び順は A（赤）→ B（黄）→ C（緑）。
- [ ] Given 既定閾値、When 原価率がちょうど30.0%のメニュー、Then 色は黄（注意閾値以上）・ラベル「注意」。
- [ ] Given 既定閾値、When 原価率がちょうど35.0%、Then 黄（危険閾値以下）。35.1%なら赤。
- [ ] Given 危険閾値を35→28に変更、When 保存、Then 原価率32%のメニューが黄→赤に即再判定される。
- [ ] Given 注意閾値30・危険閾値28 を設定しようとする、When 保存、Then 「注意閾値は危険閾値より小さくしてください」でブロック。
- [ ] Given 売価未設定のメニューと原価率40%のメニューが混在、When ダッシュボード、Then 売価未設定メニューが最上部の「要確認」に、その下に40%メニューが並ぶ。
- [ ] Given 各バッジ、When 表示、Then 色に加えてテキストラベル（良好/注意/危険/要確認）が併記される。

### 4.f CSVエクスポート＋PDF印刷【Pro】

#### 概要
メニュー・食材・原価計算書を **CSV（Excel-JP互換）** および **印刷用PDF（ブラウザ印刷）** で出力する。**Pro限定**（第5章）。

#### CSV仕様（Excel-JP互換）
- 文字コード: **UTF-8（BOM付き）**、改行 **CRLF**、区切り カンマ、値は必要に応じてダブルクォート囲み。BOM付きUTF-8により Excel（日本語版）でそのまま文字化けせず開ける。
- 出力3種:
  1. **食材マスタCSV**: 食材名 / 購入価格(税抜) / 購入量 / 単位 / 歩留まり率(%) / 有効単価(税抜) / 税率(%) / 入力税区分
  2. **メニュー一覧CSV**: メニュー名 / 売価(税込) / 売価(税抜) / 原価(税抜) / 原価率(%) / 粗利(税抜) / 材料数 / 状態(正常/要確認)
  3. **原価計算明細CSV**（材料内訳）: メニュー名 / 食材名 / 使用量 / 単位 / 有効単価(税抜) / 金額(税抜)

#### PDF（ブラウザ印刷）仕様
- `window.print()` ＋印刷用CSS。色に依存せずラベル併記（印刷は白黒想定）。出力2種:
  1. **メニュー一覧（原価率レポート）**: 全メニューの原価率・粗利・信号ラベルを表形式。出力日付を記載。
  2. **原価計算書（単品）**: 1メニューの材料内訳・原価・売価(税込/税抜)・原価率・粗利。厨房掲示や税理士提出向け。

#### 状態
- デフォルト: エクスポート/印刷ボタン（Proバッジ付き）。
- Freeロック: Free ではボタンに鍵アイコン、押下でアップセル。
- 空: メニュー/食材0件のときは出力対象なしを案内。
- 成功: CSVはダウンロード（ファイル名例 `genka-menus-YYYYMMDD.csv`）、PDFは印刷ダイアログ。

#### 受入条件
- [ ] Given Pro ユーザー、When メニュー一覧CSVを出力、Then BOM付きUTF-8・CRLFのCSVがダウンロードされ、Excel(JP)で日本語が文字化けせず開ける。
- [ ] Given Free ユーザー、When CSV/PDFボタンを押下、Then 出力されずアップセルモーダルが出る。
- [ ] Given 原価率24.8%のメニュー、When メニュー一覧CSV、Then 原価率列が「24.8」（小数第1位）で出力される。
- [ ] Given 要確認メニュー（売価未設定）、When メニュー一覧CSV、Then 原価率列は空欄または「—」、状態列は「要確認」。
- [ ] Given Pro ユーザー、When 単品の原価計算書PDFを印刷、Then 材料内訳・原価・売価(税込/税抜)・原価率・粗利・出力日が印刷用レイアウトで表示され、信号は色＋ラベル併記。

### 4.g JSONバックアップ／復元【Free でも可能】

#### 概要
全データ（食材・メニュー・設定・ライセンス）をJSONファイルとしてエクスポート／インポートする。**データ安全性＝ローカル完結ブランドの信頼のため、Free でも利用可能**（localStorageは消えうるので無料ユーザーが自衛できないのは製品として不可）。CSV/PDFとは目的が異なる（CSV/PDFは加工・提出用でPro、JSONは端末内データの丸ごとバックアップ・移行用でFree）。

#### JSONフォーマット
```json
{
  "app": "genka-dentaku",
  "schemaVersion": 1,
  "exportedAt": "2026-07-09T12:00:00+09:00",
  "data": {
    "ingredients": [ /* 食材配列 */ ],
    "menus": [ /* メニュー配列 */ ],
    "settings": { /* 閾値・税・丸め等 */ },
    "license": { /* Proライセンス。端末移行のため既定で含む */ }
  }
}
```
- ライセンスをエクスポートに含めることで、端末変更・再インストール時にProも復元できる（複数端末フローと兼用、第5章）。これはライセンスキーが共有可能であることを許容する設計（バックエンド無しの前提）。

#### インポート検証方針
- `app === "genka-dentaku"` を確認。異なれば拒否。
- `schemaVersion` を確認: 既知の旧版なら**マイグレーション**して取り込む。アプリより新しい版なら「新しいバージョンで作成されたデータです」と拒否（データ破壊防止）。
- `data` の各レコードをスキーマ検証。既定は**厳格検証＝不正があれば全体を拒否**し、現データを保持したうえで「どの項目が不正か」を提示。副次アクションとして「不正な項目をスキップして取り込む（部分復元）」を提供する。
- インポート実行前に「現在のデータは上書きされます」と確認（または「マージ／置換」を選択）。既定は**置換**（バックアップ復元の直感に合う）。

#### 状態
- デフォルト: エクスポート／インポートボタン（Freeでも活性）。
- 読込中: ファイル解析。大容量でもUIをブロックしない。
- エラー: パース失敗・スキーマ不一致・バージョン不整合を明示（第8章）。
- 成功: 復元完了後に件数を提示（例「食材12件・メニュー5件を復元しました」）。

#### 受入条件
- [ ] Given Free ユーザー、When JSONエクスポート、Then 全データを含むJSONがダウンロードされる（Freeでも可能）。

## 8. エッジケース＆エラー処理

各項目を「発生条件／期待挙動」で仕様化。すべて**アプリをクラッシュさせない・データを黙って壊さない・誤った原価を黙って表示しない**を満たすこと。

### 8.1 単位換算（次元の一致）
- **発生条件**: レシピの使用量単位が食材の購入単位と次元不一致（例: 個で買った食材をgで使用しようとする）。
- **期待挙動**: 使用量の単位セレクタを購入単位と互換な単位のみに制限し、構造的に非互換入力を防ぐ（重量→{kg,g}、容量→{L,ml}、個数→その単位のみ）。互換内はkg↔g・L↔mlを自動換算して計算。万一インポート等で非互換データが混入した場合は該当材料行に警告バッジを付け、その材料費を「不明」扱い（原価に誤って算入しない）＋修正導線。

### 8.2 歩留まり率 = 0%
- **発生条件**: 歩留まり率に0を入力（有効単価がゼロ除算になる）。
- **期待挙動**: **入力を1〜100%に制限し0を禁止**。0入力時は保存せず「歩留まり率は1〜100%で入力してください」とインラインエラー。既定値100%。

### 8.3 歩留まり率 = 100%
- **発生条件**: 廃棄ロスがない食材。
- **期待挙動**: 正常。有効単価＝購入単価（¥1000/500g→¥2.0/g）。

### 8.4 価格 = 0
- **発生条件**: 購入価格に0（無料/サービス品/未入力扱い）。
- **期待挙動**: 有効単価0・その材料費0・原価は他材料の合計。計算上は正常だが、**「価格が0の食材があります」の注意表示**を出し（意図しない未入力を検知）、クラッシュしない。原価率は他材料により算出される（0のメニューなら原価率0%＝緑だが、要確認とはしない）。

### 8.5 売価 = 0 または未設定
- **発生条件**: メニューの売価が0または空（原価率がゼロ除算）。
- **期待挙動**: 原価率を算出せず**「—」表示**、メニューを**「要確認」**扱い。ダッシュボードの**要確認グループ（最上部）**に配置。原価・粗利は計算可能なら表示（粗利は売価未確定のため「—」でも可）。クラッシュしない。一括値上げ適用では、原価が算出可能なら推奨売価を出せる対象とする。

### 8.6 材料が参照する食材の削除
- **発生条件**: レシピが参照する食材が食材マスタから削除された（ダングリング参照）。
- **期待挙動**: 食材削除時に「この食材はN件のメニューで使用中です」と警告し、削除するかを確認。削除された場合、参照する材料行に**警告バッジ**を付け、当該材料費を**「不明」**として原価計算に誤って算入しない。メニューは**「要確認」**扱い（誤った原価を黙って出さない）。修正導線（代替食材の選択 or 行削除）を提供。

### 8.7 localStorage が満杯（QuotaExceededError）
- **発生条件**: 保存時に容量超過で書き込み失敗。
- **期待挙動**: **QuotaExceededError を捕捉**し、直近の変更が保存できなかったことを明示。「JSONでバックアップを取り、不要なデータを整理してください」と案内。**保存前の状態を壊さない**（部分書き込みで破損させない）。JSONエクスポート導線を即時提示。

### 8.8 localStorage 破損
- **発生条件**: 読込時にJSONパース失敗・スキーマ不整合（外部操作・拡張機能等による破損）。
- **期待挙動**: 読込時に**検証**し、パース失敗時は**ホワイトスクリーンにしない**。「保存データを読み込めませんでした」画面を出し、(1) JSONバックアップから復元、(2) データをリセットして最初から、の2択を提示。破損データは上書きせず退避（可能なら別キーに保全）してから対応。

### 8.9 JSONインポート時の不正データ／バージョン不整合
- **発生条件**: `app` 不一致・schemaVersion不整合・レコード不正・パース不能。
- **期待挙動**: 第4.g のインポート検証方針に従う。`app`不一致/新バージョン→拒否。旧バージョン→マイグレーション。レコード不正→既定は全体拒否＋不正箇所提示、副次で部分復元。パース不能→「ファイルを読み込めませんでした」。いずれも**現データを保持**しクラッシュしない。

### 8.10 その他の境界（補足）
- **使用量0の材料行**: 材料費0として扱う（削除忘れの可能性を軽く示唆）。保存は許容。
- **極端な桁の入力**（例: 購入価格に巨大値）: 数値としてオーバーフローしない範囲で計算し、表示は丸め規則に従う。負値は禁止（インラインエラー）。
- **同名食材・同名メニュー**: 許容（内部IDで識別）。ユーザーには重複名の注意表示を任意で出す（Could）。

### 9.2 localStorage キー構成
- 単一ルートキーに全状態を集約する: **`genka-dentaku`**（値は下記構造のJSON文字列）。
```
genka-dentaku = {
  schemaVersion: 1,
  meta:        Meta,
  settings:    Settings,
  ingredients: Ingredient[],
  menus:       Menu[],
  license:     License
}
```
- 破損時退避用の予備キー: `genka-dentaku:backup`（読込失敗時に破損内容を退避）。
- 単一キー集約により、JSONエクスポート＝このオブジェクトをラップするだけで済み、整合性・バージョニングが単純化する。

### 9.3 スキーマバージョニング方針
- `schemaVersion`（整数）を単一の正とする。現行 = 1。
- 起動時: 保存版 < 現行 → **マイグレーション関数を順に適用**して現行に更新。保存版 > 現行（新しいアプリで作成）→ 読込を拒否/読み取り専用にしてバックアップを促す（データ破壊防止）。版が無い/不正 → 破損として第8.8章の復旧UI。
- インポートも同じマイグレーション経路を通す（第4.g）。
- 将来のフィールド追加は**後方互換のデフォルト補完**を基本とし、破壊的変更のみ版を上げる。

## 10. オンボーディング要件

初回起動で「白紙の壁」を避け、**最短で THE WEDGE を体験**させることが目的。詳細ビジュアルは design-spec 担当。ここでは機能要件（サンプル内容・投入/クリア挙動）を定義する。

### 10.1 初回投入の挙動
- **初回起動判定**: `meta.sampleSeeded === false` かつ既存データが空のとき、プリセット食材＋サンプルメニュー1品を投入し、`sampleSeeded = true`、`onboardingDone` は初回ガイド完了で true。
- **既存ユーザーには再投入しない**（データがある/フラグが立っている場合は投入しない）。
- サンプルの各レコードは `isSample = true`（食材にも同等のサンプル印を持たせ、一括クリア対象を識別）。
- 初回に短いガイド（1〜3ステップ）で「食材の価格を変えると原価率が動く」ことを示す導線を出す（実装粒度はdesign-spec）。

### 10.2 サンプルの投入内容（実装にそのまま使える既定値。金額は税抜、説明用の例示値）

### 10.3 サンプルのクリア／再投入
- **一括クリア**: 設定またはオンボーディング内に「サンプルデータを削除」を用意。`isSample = true` の食材・メニューをまとめて削除する（ユーザーが作った非サンプルデータは残す）。
- **再投入**: 「サンプルを入れ直す」を用意（Should）。既存の非サンプルデータは保持しつつサンプルのみ再投入。
- サンプルメニューは**3件上限にカウントされる**（Free）。ユーザーが自分のメニューを3件作りたい場合はサンプルを削除すれば枠が空く（アップセルにもこの案内を含む、第5.2）。

### 10.4 受入条件
- [ ] Given 初回起動（データ空・sampleSeeded=false）、When アプリ表示、Then プリセット食材とサンプル「唐揚げ定食」が投入され、原価率 ≒24.8%（緑）が表示される。
- [ ] Given サンプル投入済み、When 鶏もも肉の価格を¥900→¥1200に変更、Then 唐揚げ定食の原価率が ≒30.9%（黄）に即再計算される（wedge体験）。
- [ ] Given サンプルとユーザー作成データが混在、When 「サンプルデータを削除」、Then サンプルのみ削除されユーザーデータは残る。
- [ ] Given 既存データがある2回目以降の起動、When アプリ表示、Then サンプルは再投入されない。
- [ ] Given Free・サンプルメニュー1件＋自作2件＝3件、When 追加操作、Then アップセルが出て「サンプルを削除して枠を空ける」導線が示される。

## 12. 確定裁定（CPO）

第11章までの仕様に対する、CPO による最終裁定。**本章は確定事項であり、矛盾する記述に優先する。** 各裁定は本文の該当箇所にも反映済み。

### 裁定1: サブスクとオフライン鍵の整合（ハイブリッド方式）
- ライセンスキーに**有効期限＋内蔵猶予**を埋め込みローカル判定する: **月額キー≈38日**（30日＋約8日猶予）、**年額キー≈373日**（365日＋約8日猶予）。
- **年額¥9,800を主CTA**とし、料金ページのプラン切替・各アップセルCTAで年額を既定選択・前面に出す（2ヶ月分お得＋発行運用を1/12に圧縮）。
- 月額は請求サイクルごとに新キーをメール送付。**当面は手動フルフィルメント**、MVP後に **Cloudflare Worker＋Stripe webhook で自動化**。
- 期限到達時: アプリ内で**7日間の猶予バナー**を表示 → 猶予後に Free へ降格。**データは常に保持**（削除しない・閲覧編集可・新規追加のみ3件制限）。
- （PRD 5.3／5.4／11.2 に反映済み。）

### 裁定2: 時計巻き戻し・キー共有の許容度（PRD 5.4 どおり確定）
- クライアント検証のため完全防止は不可。**低価格＋善意運用前提で許容**し、ソフト検知のみ（`lastSeenDate` による巻き戻し警告、キーへの購入者参照埋め込みによる心理的抑止）。強制ロックはしない。

### 裁定3: 値上げシミュの丸め基準（PRD 第0.5章 どおり確定）
- 内部フル精度・表示丸め。シミュ推奨売価は**税抜で¥10単位切り上げ**（実効原価率が目標以下＝安全側）、**税込換算を併記**。
- **税込基準の丸めオプションは v1 対象外（post-MVP バックログ）。** v1 は税抜丸め＋税込併記で固定。

### 裁定4: JSONバックアップにライセンスを含める（含める＝確定）
- 端末移行 UX が共有リスクを上回る（善意ユーザーモデル）ため、**ライセンスをエクスポートに既定で含める**。
- **除外オプションは v1 では設けない**（シンプルさ優先）。

### 裁定5: サンプルメニューの3件上限カウント（カウントする＝確定）
- サンプルメニューは **Free の3件上限にカウント**する。削除すれば枠が空く（PRD 10.3／5.2 どおり）。上限ロジックにサンプル特例を作らない。

### 裁定6: 既定税率・入力方式（PRD 第0.3章 どおり確定）
- 食材＝**8%税込入力**・売価＝**10%税込入力**を既定。内部は税抜正規化。
- テイクアウト主体店は**設定変更のみ**で対応（開業時アンケート等の導線は v1 では作らない）。明細行ごとの複数税率は対象外。

### 裁定7: サンプルの具体値（PRD 10.2 の値で確定）
- 第10.2 の食材・レシピ値を採用。**緑(≈24.8%)→黄(≈30.9%)を跨ぐ**設計（鶏もも ¥900→¥1200）を維持し、wedge 体験の教育効果を担保する。
