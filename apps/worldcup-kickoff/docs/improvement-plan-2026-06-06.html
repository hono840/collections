エグゼクティブサマリー

  • 体制：UI/UX デザイナー専任が不在。frontend-design プラグイン（導入済み確認）を活用し ui-ux-designer エージェント新設を提案。

1【最優先】エージェント受け渡しで止まった問題

1-1. 観測された症状

  • 「今から起動します／再起動します」と 宣言した直後に何も起こらず、ユーザーに 動いてる？ また止まったよね と複数回確認させてしまった。
  • フェーズの境目（例：サブエージェントへの指示文「…10行以内で報告」を書いた直後）で進行が止まって見えた。
  • 引き継ぎの取り違え：「もう委譲は不要、次は最終検証」と言いながら、直後に「最新ビルドで起動し直したい」＝残作業があるのに着手せずターンを終えた。
  • 体制面：UI/UX デザイン専任がおらず、見た目・装飾の判断が場当たりになりがち。

1-2. 根本原因（3類型）

原因A：ツール呼び出しエンベロープの破損（最頻・最重大）

ツール呼び出しを 正規の関数呼び出し構造 ではなく、見た目だけ似た “ただのテキスト”として出力 してしまった。結果、ターンが「発言だけ」で終了し、サブエージェントもコマンドも 起動されない。エラーにもならないため、外からは「宣言したまま無言で停止」に見えた。
※ 正しい構造で送った同じ指示は毎回成功している。つまり指示内容ではなく 送信形式 の問題。

原因B：特殊文字によるパースエラー（"malformed and could not be parsed"）

ツール引数の値に以下が含まれると呼び出しのパースに失敗した：

  • 角括弧 [ ]（例：Tailwind の max-w-[480px] や webkit セレクタをプロンプト本文に直書き）
  • 複雑なシェル一行：バックグラウンド &、%{http_code} 書式、for … do … done ループの併用

→ 角括弧を外し、シェルを単純化したら 即成功。再現性のある原因。

原因C：「予告して終了」アンチパターン＋失敗時に再試行しない

「今から起動します」を 発言の最後 に置き、ツール呼び出しを同一ターンに含めない／結果を待たずに終える運用だった。Aで実行に失敗しても 自動で直して送り直さず ユーザー入力待ちになり、停止が長引いた。引き継ぎ宣言と実残作業のズレの遠因にも。

1-3. 解決策

#対策内容効く原因
S1予告と実行を同一ターンに「起動します」で発言を終えない。必ずツール呼び出しでターンを終える。実行→結果確認→次のループを厳守。A,C
S2特殊文字の回避Agent/Bash 引数に角括弧・Tailwind arbitrary 値・複雑シェルを直書きしない。シェルは一時スクリプト化、Tailwind 値はプレーン文で説明。B
S3失敗の即時リトライ"malformed" や無実行を検知したら同一ターンで形式を直して即再送。「止まった？」と言わせない。A,B
S4Workflow での決定論的オーケストレーション多段委譲（/new-app 相当）は Workflow スクリプト（pipeline/parallel）で1スクリプトに固めて自動実行し、人手のシリアライズミスを原理的に排除。※ 明示オプトイン前提。A,C
S5完了条件の明示各委譲後に結果が返ったか確認してから次へ。宣言と残作業を取り違えず、宣言したらその場で着手。C
S6UI/UX デザイナー新設CPO 配下に ui-ux-designer を新設し、導入済み frontend-design を活用。視覚・装飾・一貫性を専任化。体制

1-4. 再発防止チェックリスト

  1. ツール呼び出しは正規構造で1ブロックずつ。発言の締めは実行か結果報告。
  2. 引数に [ ]・生の &・%{…}・ループを入れない。必要ならスクリプト化。
  3. 呼び出しが実行されなかったらそのターン内で直して再送（持ち越さない）。
  4. 「次は◯◯」と言ったら同じターンでその一歩を実行する。
  5. 3段以上の委譲は Workflow を検討。
  6. 各サブエージェント完了時は結果を一行で再陳述してから次へ。

2拡張要素の改修プラン

2-1. P1worldcupapi.com 連携の調査と方針

観点内容
データ種別ライブスコア／予定試合・ラインナップ・試合前統計／過去データ・対戦成績／ライブオッズ（賭けオッズ）
2026 W杯「FIFA World Cup 2026」と明記（開催国の詳細は記載なし）
形式RESTful・JSON。"sub-second"・リアルタイムを標榜
認証/料金API キー必須。無料枠・料金は「記載なし」
サンプル/規約レスポンス例・利用規約・ライセンスはすべて「記載なし」

判定と懸念

  • 不透明：料金・無料枠・ライセンス・サンプル未記載で依存先としての信頼性を評価できない。
  • オッズ中心：本アプリは初心者向け・非賭博。オッズは不要かつ規約/年齢/地域規制の観点で避けたい。
  • 現状の openfootball/world-cup.json（無料・パブリックドメイン・48カ国/104試合/16会場 完備・稼働中）が依然最良の土台。

方針（既存設計を活かす）

  1. 静的データを source of truth に維持。WorldCupRepository 抽象化によりライブAPIは後付けで差し替え可能（liveRepository）。順位計算は computeStandings() に隔離済みで置換も容易。
  2. フェーズ1（開幕前〜）：静的のまま。結果反映は手動 or 後日。追加コスト 0。
  3. フェーズ2（開幕後・任意）：ライブスコアのみ追加。無料枠・規約が明示された football-data.org（第一候補）／ API-Football（$19・15秒更新）を優先。worldcupapi.com は料金・ToS・サンプル確認後。オッズは使わない。
  4. オッズ・賭博系は本アプリでは扱わない方針を明文化。

担当：CFO/cost-analyzer（料金確認）→ backend-developer → security/supply-chain。

2-2. P0tier（優勝候補/ダークホース/チャレンジャー）の根拠を明記

  • 現状：バッジは CountryListItem で表示（favorite→優勝候補 / darkhorse→ダークホース / underdog→チャレンジャー）。割当ては src/data/countries-content.json に手動。「なぜその tier か」「各 tier の意味」が示されていない。

改修プラン

  1. (基準の明文化)
    • 優勝候補：優勝経験・FIFAランク上位・近年の安定実績（ブラジル/アルゼンチン/フランス/スペイン/イングランド…）
    • ダークホース：上位を脅かす実力・勢い（モロッコ/日本/アメリカ…）
    • チャレンジャー：初出場や格上への挑戦（キュラソー/カーボベルデ/ヨルダン/ウズベキスタン…）
  2. (データ追加) countries-content.json に各国 tierReasonJa（一言の理由）を48カ国分追加。型 Team・repository マージにも反映。
  3. (UI と導线) TierLegend を新設（モーダル or /countries 上部の凡例）。3 tier の意味＋基準を解説。バッジ tap → 凡例モーダル（TermPopover 作法を踏襲）。国詳細に「なぜ◯◯？」= tierReasonJa を表示。
  4. (注記)「初心者向けの目安・編集部の主観」と明記し序列の断定と誤解されないように。

担当：content-creator（基準文＋48カ国 tierReasonJa）／ ui-ux-designer＋frontend-developer（凡例UI・導线）／ backend-developer（型＋repository）。

2-3. P1PC 表示の左右余白に W杯らしい装飾

現状：layout.tsx は max-w-[480px] 中央寄せ。デスクトップで左右が大きく空いて寂しい。

改修プラン

  • モバイルは現状維持。装飾は lg 以上でのみ表示。
  • lg+ で中央アプリ枠の左右に装飾 aside／背景レイヤを追加。モチーフ：ピッチの芝目、紙吹雪、各国国旗の縦帯、ボール、トロフィー、開催国（米国・カナダ・メキシコ）のシルエット等。
  • 素材は自作 SVG / CSS で生成（写真は著作権リスクのため不使用）。aria-hidden・pointer-events-none・overflow-hidden・prefers-reduced-motion 配慮。
  • 実装：layout.tsx に最背面の装飾レイヤ＋左右 aside、または DecorativeBackdrop organism に切り出し。本文の可読性・コントラスト最優先。
  • frontend-design スキルで凡庸なAIデザインを避け、ブランド（ピッチグリーン＋ゴールド）に沿った上質なビジュアルに。

担当：ui-ux-designer（ビジュアル設計）／ frontend-developer（実装・A11y）。

4リスクと留意点

  • worldcupapi.com：料金・無料枠・ライセンス不明。確認まで本番依存にしない。オッズ不採用。
