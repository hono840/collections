## 目的

1. **登録したスポットの「メモ」を、あとから編集できるようにする。**（段階1）
2. **データをユーザーごとにサーバー（Supabase のデータベース）へ保存する。** 端末を変えても、Safari の「7日使わないと保存データを消す」決まりがあっても、データが残るようにします。（段階2〜6）

段階1はいまの localStorage（ブラウザの中の保存場所）のままで作れます。データベースとは関係がないので、先に作って公開できます。

## 段階2〜6 データベース（Supabase）に保存する

### 仕組み

目的は「本人のデータを、どの端末からでも本人だけが読み書きできる」ことです。

- そのために、データをサーバー（Supabase のデータベース）に置きます。
- サーバーで誰のデータかを見分けるために、ログイン（Supabase Auth）を入れます。
- 他人のデータを読めないように、テーブルに RLS（Row Level Security：データ1件ごとの鍵）を付けます。「`user_id` が自分のものだけ」読み書きできるようにします。
- 公開先は GitHub Pages のままです。ブラウザから直接 Supabase と通信するので、サーバーを増やしません。

### 調べて分かったこと（2026-10-25）

| 区分 | 内容 | 出典 |

### ここから分かる注意点（推論）

1. **ホーム画面のアプリでは「メールのリンクでログイン」がうまくいかない可能性が高い。** メールのリンクは Safari で開きます。でも、ログインの途中の情報はホーム画面のアプリ側に残っています。PKCE は同じブラウザで完了させる必要があるので、つながりません。そのため、ログイン方法は「メール＋パスワード」が第一候補です。
2. **このアプリだけで、プロジェクトを2つ使う。** 本番のデータベースではテストをしない決まりなので、開発用と本番用を分ける必要があります。Docker（パソコンの中に別の環境を作る道具）は使わない方針なので、開発用もクラウドに作ります。いま無料枠の2つが空いているかは**未確認**です。
3. **無料プランだと、使う人が少ないと7日で止まる。** 止まっている間は、データの読み込みも保存もできません。
4. **山道は電波が弱い。** データベースだけにすると、電波が無い場所では一覧も見られません。
5. **ほかの人にも使ってもらうなら、メールアドレス（個人情報）を預かることになる。** 何のために使うかをアプリの中で説明する必要があります。
6. **ログインの情報も、ブラウザの中に保存される。** Safari の7日ルールで消えても、データはサーバーに残ります。もう一度ログインすれば戻ります。

### 作るもの（案。D1〜D8 で変わる）

- **テーブル `spots`**: `id`（自動の連番）・`user_id`（ログインした人の ID、初期値は `auth.uid()`）・`name`・`region`・`category`（5種類のどれか、データベースで検査）・`distance_km`・`season`・`memo`・`done`・`created_at`・`updated_at`。
- **並び順**: 新しい順（`created_at` の大きい順）。v1 の「先頭に追加」と同じ見え方にする。
- **RLS**: 読む・足す・変える・消すの4つとも「`user_id = auth.uid()` の行だけ」。ログインしていない人は何もできない。
- **データの引っ越し**: ログインした直後、この端末の localStorage に `drive-spots:v1` があって、初期データのままでなければ「この端末のデータをアカウントに入れますか」と聞く。入れたら、二重に取り込まないように印を付ける。localStorage 側のデータはすぐには消さない。
- **CSP**: `connect-src` に `https://<プロジェクトの ref>.supabase.co` を足す。v1 の AC21「外部への通信ゼロ」を「通信先は Supabase だけ」に書き換える。
- **鍵**: Supabase の URL と publishable key は、ビルドのときに GitHub Actions の変数から入れる。secret key は使わない。ブラウザ・リポジトリ・手元のファイル（`.env.local` など）のどこにも置かない。
- **テスト**: 本番のデータベースにはテストを流さない。RLS のテストは開発用のプロジェクトで、テスト用のユーザーを使って行う。テストのあとは片付ける。

### 進め方（承認ゲート）

- 本番の Supabase を作ること、ログインを有効にすること、鍵の設定は「本番環境・認証・鍵の変更」に当たります。作業の前に「何をするか・何が危ないか・ほかの案」を出し、CTO と security-auditor のレビューを通して、Hiro の承認をもらってから行います。
- road-review の Supabase（本番の変更は禁止）には触りません。
- 本番の設定を変えたら、実際にログインできることと、他人のデータが読めないことを確かめるところまでを1つの作業とします。
